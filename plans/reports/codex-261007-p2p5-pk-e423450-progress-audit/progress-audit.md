Two shutdown defects still need correction:

1. **The request timeout bounds waiting, not request lifetime.** After two ticks report `stop/verify timeout`, both original workers remain alive. A separate child prints that its tick and main body completed, yet the interpreter fails to exit before an outer 0.5 s limit because the worker remains blocked. `shutdown(wait=False, cancel_futures=True)` does not cancel a running future. This agrees with the [Python executor documentation](https://docs.python.org/3.12/library/concurrent.futures.html#concurrent.futures.Executor.shutdown). Repeated ticks can accumulate outstanding workers and delayed actions. Use real transport deadlines or explicitly owned subprocesses that are terminated and reaped at the request deadline. Preserve parallel attempts; test several hung targets across repeated ticks and verify that no unbounded workers remain. A process-pool executor with the same cancellation pattern is insufficient. The controller's self-stop path also needs a bounded request policy.

2. **Terminal cleanup evidence is written after self-stop.** `control()` calls `control_tick()`, which invokes `self_stopper`, and only afterward writes the outcome map to the ticks Dict. In the fully mocked integration, self-stop immediately terminates the child; the event trace contains the target stop and controller stop, but no persisted tick map. In particular the unresolved target/fallback evidence is lost. This is a local termination-order counterexample, not an assertion about a freshly tested Modal shutdown. Emit structured terminal intent and unresolved outcomes before self-stop and retain them through a bounded persistence path; evidence writes must not indefinitely delay shutdown. Test immediate termination, hung self-stop, and evidence-write failure. Do not label self-stop intent as independently verified app shutdown.

The final orchestration also must enforce the newly assumed launch windows. Slot spawn/admission currently does not consult controller state or horizon. A valid slot deadline later than the controller fallback remains admissible; the terminal tick classifies that future app as `not due`, has no unresolved targets, and self-stops. Bind each app's deadline and admission to the immutable campaign/control identity and permitted spawn window; enforce the validation/setup and latest readings-start boundaries. This is remaining package work, and the arithmetic correction alone does not clear it.
